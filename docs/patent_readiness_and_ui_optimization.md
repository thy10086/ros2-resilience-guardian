# 专利准备与工业安全产品化路线

> 本文用于技术交底和研发规划，不替代专利代理师的法律意见。正式申请前应由代理师基于完整源代码、实验数据和检索结果定稿。

## 1. 中国软件相关发明专利的准备重点

截至 2026 年 9 月，软件相关方案应按“计算机程序相关发明”准备，而不是把“软件代码本身”作为唯一保护对象。技术交底需要说明：

1. 现有技术解决不了的具体技术问题；
2. 运行在计算机、ROS 2 节点、机器人控制器或安全网关上的具体技术手段；
3. 由这些技术手段产生的可验证技术效果；
4. 方法、系统/装置、设备和计算机可读存储介质之间的对应关系。

仅描述业务规则、抽象评分公式或“使用人工智能判断”通常不足以形成稳定的保护范围。Jev 在本项目中应被写成可选的语义辅助模块，不应成为实时停车、限速或恢复的必要条件。

申请文件至少应准备：

- 发明专利请求书；
- 说明书；
- 权利要求书；
- 说明书摘要；
- 必要的附图、流程图、时序图和系统结构图；
- 申请主体、发明人、优先权和委托代理信息。

正式申请前应避免在论文、演示、开源仓库或公开演示中泄露尚未申请的关键技术组合。已有公开内容应作为现有技术和本项目时间线的一部分记录，不能直接当作新的独立创新点。

## 2. 本项目适合形成的技术方案组合

当前项目不建议把“ROS 2 安全驾驶舱”或“Jev 调用”单独作为核心创新点。更适合围绕确定性的安全闭环组织一组技术方案：

### 方案 A：因果风险图与证据账本绑定

- 将 ROS 2 节点、话题、传感器和执行器组织成带信任域、关键度、关系出处和传播权重的运行时因果图；
- 以经过来源、时序和重放校验的事件作为风险种子；
- 沿图传播到执行器，记录完整路径、图指纹和证据父子关系；
- 对图变化、证据失效和账本篡改触发重新评估。

### 方案 B：延迟补偿的预测安全速度包络

- 同时使用当前速度、可用距离、制动能力、控制延迟、传感器延迟、预测风险增长和测量不确定度；
- 计算安全速度上限，而不是只用固定风险阈值；
- 传感器过期、输入非有限、制动距离不足或预测风险超过停车阈值时强制 `SAFE_STOP`；
- 用仿真数据证明风险增长或延迟增加时，速度上限单调下降。

### 方案 C：上下文绑定的双阶段恢复协议

- 经过 `SAFE_STOP → RECOVERY_PROBING → RECOVERY_CANDIDATE → RESUMABLE` 状态转换；
- 恢复条件同时检查攻击是否消失、拓扑是否稳定、传感器是否新鲜、旧命令是否清空、策略是否有效；
- 生成绑定图指纹、策略指纹、账本锚点和命令代次的一次性有期限恢复凭据；
- 上下文变化、时间回退、凭据重放或过期自动回到 `SAFE_STOP`。

### 推荐的权利要求层次

1. 独立方法权利要求：覆盖 A + B + C 的闭环关系；
2. 独立系统/装置权利要求：覆盖事件验证、因果图、证据账本、风险包络、恢复门控和执行边界；
3. 独立设备或存储介质权利要求：覆盖程序被执行时实现上述方法；
4. 从属权利要求：限定 ROS 2 话题映射、图指纹、重放拒绝、预测速度计算、一次性凭据和安全状态回退；
5. 可选从属权利要求：Jev 只接收有界摘要并返回语义分类/人工复核建议，不能解除安全状态。

## 3. 申请前必须补齐的工程证据

目前已有离线确定性实验和工业 Python 静态检查，但距离高质量技术交底还应补齐以下证据：

| 优先级 | 需要补齐的证据 | 最低可接受结果 |
| --- | --- | --- |
| P0 | 与固定阈值策略对比 | 延迟、风险增长、可用距离变化时，本方案更早限速或停车 |
| P0 | Gazebo/Webots/ROS 2 仿真闭环 | 同一攻击输入下记录检测延迟、停车提前量和任务结果 |
| P0 | 误报与漏报数据集 | 每条样本有攻击类型、来源可信度、期望状态和实际状态 |
| P0 | 恢复安全性 | 恢复凭据不可重放，图变化或父证据失效时回到停车 |
| P1 | 资源开销 | 记录 CPU、内存、图刷新耗时、账本写入耗时和 ROS 2 延迟 |
| P1 | 工业代码检查覆盖 | 增加 C++、launch、YAML、SROS 2/DDS 权限和依赖扫描 |
| P1 | 规则版本与审计 | 每次结果保存规则版本、源码哈希、样例哈希和检查时间 |
| P2 | 现有技术检索矩阵 | CNIPA、WIPO、Google Patents、Nav2 Collision Monitor 等逐项对比 |

关键实验输出应保存为结构化 JSON，同时生成带版本和哈希的 HTML/PDF 报告，避免只保留截图。

## 4. 工业代码安全检查的产品化优化顺序

### 第一阶段：上线前检查闭环

- 增加规则配置文件和规则版本；
- 支持 `AMR 导航`、`机械臂/夹具`、`输送线` 三个安全 profile；
- 输出源码哈希、规则版本、检查时间和报告 ID；
- 增加“修复后重新检查”的前后对比；
- 导出 JSON、SARIF 和工程审查报告；
- 对执行器主题建立“代码发布点 → Guardian 安全边界”的映射。

### 第二阶段：工业工程适配

- 支持 `.cpp`、`launch.py`、`.yaml` 和 SROS 2/DDS 权限文件；
- 检查 QoS、参数动态修改、外部进程调用、未受限服务、TF/传感器新鲜度和控制频率；
- 生成依赖清单和 SBOM；
- 引入 Gazebo/Webots 仿真回归，检查静态风险是否在运行时真正触发；
- 把检查结果接入 CI，阻止带 `critical` 风险的构建产物进入部署阶段。

### 第三阶段：审计和协同

- 工程师复核、批准、驳回和复测记录；
- 风险接受必须填写原因、责任人和有效期；
- 版本之间保留证据链；
- 支持按机器人、任务、组件和执行器主题查询历史趋势。

## 5. 本轮已经完成的前端可理解性优化

- 工业代码结果先显示“上线建议”，不再先展示规则编号；
- `BLOCKED / REVIEW / PASS` 转换为“禁止上线 / 整改后复核 / 可以进入下一步测试”；
- 增加“发现问题、必须阻断、高风险、待复核”四个直观数字；
- 完整规则、代码行、证据和修复建议收进“查看技术证据”；
- Jev 指标改成“风险倾向、判断把握、对机器人任务的影响、是否需要人工确认”；
- 保留原始语义标签，方便工程审计；
- 将实时页的 `ψ / δ / γ` 改成中文解释，并保留括号内符号；
- 增加窄屏布局，避免必须横向滚动才能理解主结论。

## 6. 不应在产品中混淆的边界

- 静态规则是本地确定性证据；
- Jev 是可选的远程语义辅助证据；
- Jev 不能解除 `SAFE_STOP`、修改速度上限、发布 `/cmd_vel` 或代替人工批准；
- “风险分数低”不等于“机器人一定安全”，必须同时满足来源可信、执行器边界、任务许可、传感器新鲜和恢复条件；
- 专利可申请性、新颖性和创造性必须由代理师基于检索结果确认，项目页面不应显示“已获得专利”之类结论。
