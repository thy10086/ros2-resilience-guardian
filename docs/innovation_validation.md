## 实验结果

### 1. 零信任事件门

验证来源、时间戳、未来时间、序列号重放和 HMAC 签名。

| 输入 | 结果 |
| --- | --- |
| 可信事件 | `ACCEPTED` |
| 未知来源 | `UNKNOWN_SOURCE` |
| 过期事件 | `STALE` |
| 未来时间事件 | `FUTURE` |
| 重复序列号 | `REPLAY` |
| 正确 HMAC | `ACCEPTED` |
| 错误 HMAC | `INVALID` |

共阻止 5 类不可信事件，说明攻击事件不会绕过验证器直接进入风险引擎。

### 2. 计划生效前的多波重新规划

第一波左右机械臂攻击生成 `ISOLATE_COMPONENT(left_arm)` 计划，激活时间为 `t=1.0`。在计划生效前 `t=0.5` 插入关键组件 `left_wheels` 攻击，系统生成新的计划 `ISOLATE_COMPONENT(left_arm,left_wheels)`，激活时间更新为 `t=1.5`。

验证结果：

- 生效前完成 2 次规划；
- 新旧计划 ID 不同；
- 新计划包含新出现的关键组件；
- 执行隔离后残余风险下降；
- 恢复评估得到 `NONE + RESUMABLE`。

这验证了新攻击到达时不会继续执行已经过时的隔离计划。

### 3. 安全状态机和任务门控

| 条件 | 状态 | 任务允许 | 速度上限 |
| --- | --- | --- | --- |
| 无攻击 | `NORMAL` | 是 | `0.35 m/s` |
| 单个非关键攻击 | `RESUMABLE` | 是 | `0.35 m/s` |

结果证明风险评估、缓解动作和任务放行之间存在独立的安全策略边界。

### 4. 驾驶舱状态与审计链

使用 ROS 2 消息形状的测试消息写入风险、缓解和安全状态，验证 `/api/state` 对应的缓存结构：

- 时间线顺序为 `safety → mitigation → risk`；
- 状态快照包含 `risk`、`mitigation`、`safety`、`timeline`、`updated_at`；
- 两条审计事件能够写入 JSONL 并重新读取。

之前的真实进程 smoke test 还验证了 `guardian_dashboard` 的 `/api/health`、`/api/state` 和 HTML 页面可访问。

### 5. 跨层图风险、时序策略、证据融合和恢复门控

这一组实验把新的安全层串成一条确定性的离线链路：攻击风险从 `nav` 节点沿 `nav → /cmd_vel → base` 传播，时序监控检查来源、序列号和新鲜度，证据融合把规则结果和图风险转成统一等级，速度包络将等级映射成速度上限，恢复门控最后决定是否允许解除停车。

实验结果：

| 检查 | 结果 | 含义 |
| --- | --- | --- |
| 图传播 | `nav=0.9`、`cmd_vel=0.81`、`base=0.648`；`base` 被标为关键节点 | 风险会沿数据路径到达执行器，且输出受 `[0,1]` 约束 |
| 时序策略 | 合法消息通过；错误来源、重放、过期消息分别得到 `UNTRUSTED_SOURCE`、`REPLAY`、`STALE` | 不可信数据不会直接参与后续安全决策 |
| 多源融合 | 融合分数 `0.4046`，等级 `CONTAIN` | 图风险、时序违规和任务关键性被联合解释 |
| 速度包络 | 低风险约 `0.3325 m/s`；融合风险约 `0.2084 m/s` | 风险升高时速度上限下降，任务进入受控状态 |
| 传感器新鲜度 | 传感器过期时 `SAFE_STOP`、速度 `0` | 安全边界优先于继续执行任务 |
| 恢复门控 | 缺少 `graph_stable` 时拒绝恢复；六项条件齐备时允许恢复 | 停车解除需要多条件证据，不由单个信号触发 |

实验脚本的每个阶段都有断言，并把完整证据写入 `experiments/results/innovation_validation.json`。这组结果验证的是纯 Python 安全核心的行为和接口，尚未证明真实 ROS 2 网络图、DDS 身份策略或 Webots 底盘已经消费这些决策。

## 当前结论

已经验证的创新层包括：事件可信验证、攻击生命周期接入、计划生效前的多波重新规划、独立安全状态机、只读驾驶舱状态聚合和审计输出，以及图风险传播、时序规则、多源证据融合、风险自适应速度包络和恢复门控。

## 实验过程解释

### 为什么先验证事件门

风险引擎只能处理可信输入。如果未知来源、过期消息或重放消息进入风险引擎，后续的隔离和停车决定可能被攻击者操纵。因此实验先构造一条合法事件，再逐项改变来源、时间和序列号，最后使用相同密钥验证正确和错误 HMAC。断言检查的是“拒绝原因”，不只是拒绝布尔值，这样可以确认安全策略走到了正确分支。

### 为什么在计划生效前插入新攻击

只在攻击发生后立即规划，无法证明系统能处理计划延迟期间的状态变化。实验在 `t=0.0` 生成机械臂隔离计划，在 `t=0.5`、计划 `t=1.0` 生效前插入关键车轮攻击。若系统继续执行第一份计划，车轮攻击会被漏处理；实际结果是生成了新的计划、更新激活时间并扩大隔离集合，证明计划签名变化会触发重新规划。

### 为什么验证任务门控

风险分数本身不能说明机器人是否可以继续运动。实验分别构造无攻击、可容忍非关键攻击、需要局部隔离和不可隔离关键组件四种状态，检查状态、速度上限和 `mission_allowed` 是否同时满足预期。这样可以验证风险评估与执行边界之间没有“只报警不限制”的断层。

### 为什么把驾驶舱和审计单独验证

驾驶舱不参与安全决策，但它承担运行观测和事后分析职责。实验先按 ROS 2 消息字段写入三类状态，再检查 API 快照中的最新值、时间线顺序和关键字段，最后重新读取 JSONL 审计记录。状态缺失或顺序错误都会使实验失败。

### 为什么增加跨层融合实验

单独验证风险分数或单独验证消息新鲜度，无法说明安全措施是否真的影响执行边界。跨层实验刻意保留每一层的输入和输出：先看风险能否到达关键执行器，再确认不可信消息会被拒绝，然后将剩余证据融合成可解释等级，最后检查速度限制、停车和恢复门控是否一致。这样后续接入 ROS 2 时可以逐层替换输入并定位回归，而不必把整套系统当成不可观测黑盒。
